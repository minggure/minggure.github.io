경기 이벤트 기반 대규모 선착순 쿠폰 발급

LG U+ URECA 종합 프로젝트 우수상

실시간 경기 이벤트와 연결된 단계형 쿠폰 발급, 장애 복구, 관리자 통계 구조를 구현하고 검증했습니다.

제가 맡은 범위

  • Redis Lua Script 기반 재고 차감과 회차별 중복 신청 방지
  • MySQL 신청 이력·사용자 쿠폰·Outbox를 하나의 트랜잭션으로 저장
  • Redis 장애 시 Fail-Closed 응답과 MySQL 기준 재고 재구축
  • 단계형 쿠폰 오픈과 SSE 재고 갱신
  • Kafka 기반 관리자 일별 발급 통계와 Outbox 재처리·멱등 처리
  • 통합·동시성·장애·부하 테스트 및 결과 문서화

핵심 처리 흐름

Redis의 성공은 자리 선점이고, 쿠폰 발급 성공은 MySQL 커밋 완료입니다. Kafka와 SSE는 커밋 뒤에 이어지는 후속 처리라서 잠시 중단돼도 이미 발급된 쿠폰 자체는 사라지지 않습니다.

검증 결과

조건 결과 참고
고유 사용자 20,000명, 재고 10,000장, 60초 Ramp 성공 10,000 / 품절 10,000 20,000명이 한순간에 동시에 들어온 Burst 테스트는 아님
Windows 네이티브 k6 전송 실패 0 / 예상 밖 응답 0 부하 발생기 Docker·WSL NAT 경로를 제거한 결과
응답 시간 평균 336.95ms / p95 951.19ms 테스트 환경 기준
대량 정합성 스냅샷 사용자 1,000,003 / 신청 3,517,209 / 쿠폰 797,209 초과·중복·고아 레코드 등 검사 항목 모두 0

기술적 판단과 문제 해결

1. Redis를 썼지만, Redis 성공을 발급 완료로 보지 않은 이유

문제 짧은 시간에 요청이 몰리면 DB 락만으로 재고를 차감하는 동안 경합이 커집니다. 반대로 Redis 결과만 믿으면 Redis와 MySQL 사이에 데이터가 어긋날 수 있습니다.

선택 Redis Lua Script가 중복 확인과 재고 차감을 원자적으로 처리하고, MySQL 트랜잭션이 신청 이력·실제 쿠폰·Outbox를 확정하도록 역할을 나눴습니다.

결과 Redis는 빠른 입장 정리를 맡고 MySQL은 최종 원장을 맡습니다. DB 저장이 실패하면 선점한 Redis 재고를 되돌립니다.

한계 당첨자 한 명마다 MySQL 동기 저장은 남아 있습니다. 더 큰 규모에서는 비동기 확정 모델과 사용자에게 보여줄 PENDING 상태까지 함께 설계해야 합니다.

2. Redis가 죽었을 때 503으로 닫고 MySQL에서 복구한 이유

문제 Redis가 비어 있거나 멈춘 상태에서 DB 경로로 우회 발급하면 같은 쿠폰을 두 경로가 다르게 판단할 수 있습니다.

선택 발급 요청은 503으로 차단하는 Fail-Closed 정책을 적용했습니다. 복구는 MySQL의 실제 user_coupon을 기준으로 남은 재고, 이미 당첨된 사용자, 회차 문맥을 Redis에 다시 구성합니다.

검증 재고 100장 중 20장 발급 → Redis 중단 → 503 확인 → 복구 재고 80장 → 나머지 80장 발급 → 101번째 품절을 확인했습니다. 초과 발급과 중복 발급은 0건이었습니다.

한계 다중 인스턴스가 동시에 복구를 시작하지 않도록 분산 조정 정책을 더 명확하게 만들 필요가 있습니다.

3. 발급 성공마다 같은 행을 갱신하던 병목 제거

현상 재고 5,000장 테스트에서 실제 쿠폰은 5,000장 저장됐지만 615개 요청이 정상 응답을 받지 못했습니다.

관찰 Hikari 활성 커넥션 19/20, 최대 대기 178건, 행 잠금 2,914회/분, 잠금 대기 1,115초/분이 확인됐습니다.

원인 모든 성공 요청이 success_count 한 행을 갱신하면서 쿠폰 생성과 무관한 직렬 대기열이 생겼습니다.

개선 발급 트랜잭션에서 해당 갱신을 제거했습니다. 집계는 user_coupon을 근거로 5초 단위 그룹 집계하고, 인덱스와 MySQL Named Lock으로 중복 집계를 막았습니다.

4. 서버가 아니라 부하 발생기 네트워크가 병목이었던 사례

현상 20,000 VU 테스트에서 약 6,000건의 전송 실패가 반복됐습니다. 커넥션 풀을 늘리고 부하를 두 대로 나눠도 사라지지 않았습니다.

원인 Docker 안의 k6 요청이 Docker·WSL NAT를 한 번 더 통과했습니다. 서버 로직에 도달하기 전 부하 발생기 쪽 소켓 경로가 먼저 포화됐습니다.

변경 서버 코드는 유지하고 k6만 Windows에서 직접 실행했습니다.

결과 전송 실패 6,216건 → 0건, p95 1.84초 → 0.95초로 바뀌었습니다. 이 수치는 서버 코드 최적화가 아니라 측정 경로 정상화의 결과로 구분해 기록했습니다.

5. Kafka를 핵심 발급이 아닌 관리자 통계에 둔 이유

문제 관리자 대시보드 요청마다 634,917건을 GROUP BY로 다시 읽어 응답이 느렸습니다.

선택 쿠폰 발급은 MySQL 커밋으로 끝내고, 커밋된 Outbox 이벤트만 Kafka로 전달했습니다. Consumer는 KST 일별 통계를 미리 누적하고 API는 7일 조회 시 집계 결과 7행만 읽습니다.

결과 같은 로컬 MySQL의 쿼리 구간이 447ms → 0.0296ms로 줄었습니다. 원격 API 전체 응답 시간이 아니라 DB 쿼리 구간 비교입니다.

방어 Kafka가 멈춰도 발급은 유지됩니다. Outbox 재처리와 messageId 멱등 처리로 통계 누락·중복을 보완했습니다.

Redis TTL 기반 좌석 임시 선점

MINGPARK는 공연 예매 대기열부터 좌석 선택, 포인트 결제와 환불까지 구현한 3인 팀 프로젝트입니다. 팀장과 백엔드를 맡아 공연·회원·예매 도메인의 초기 구조를 잡고, Redis를 이용한 좌석 선점과 만료 처리를 구현했습니다.

확정된 예매는 MySQL에, 시간이 지나면 사라져야 하는 선점은 Redis에 저장했습니다.

좌석을 선택한 사용자에게만 5분의 결제 시간을 주고, 결제하지 않으면 별도 정리 작업 없이 좌석이 다시 열립니다.

제가 맡은 범위

  • 프로젝트 초기 패키지와 Controller–Service–Repository 구조 구성
  • 회원·예매 도메인과 상태 Enum 설계
  • 공연 조회·등록·수정·삭제와 공연별 기본 좌석 생성
  • MySQL 좌석 상태와 Redis 임시 락을 합친 실시간 좌석 조회
  • SET NX + TTL 기반 좌석별 5분 임시 선점
  • 결제 만료·실패·사용자 이탈 시 좌석 해제 흐름
  • 결제 화면의 남은 시간 표시와 만료 안내
  • k6 예매 요청 시나리오와 기능 브랜치 통합

기술적 판단과 문제 해결

왜 DB 상태 변경과 해제 스케줄러 대신 Redis TTL을 썼는가

문제 좌석을 누를 때마다 DB를 HOLD로 바꾸고 스케줄러가 만료 좌석을 찾아 해제하면, 짧은 임시 상태 때문에 쓰기가 늘어납니다. 서로 다른 시점에 잡힌 좌석이 같은 배치에서 풀리는 문제도 있었습니다.

선택 좌석마다 lock:seat:{seatId} 키를 만들고 값에는 선점한 회원 ID를 저장했습니다. setIfAbsent가 키 생성과 5분 TTL 설정을 한 번에 처리하므로 같은 좌석에서 첫 요청만 성공합니다.

동작 MySQL은 AVAILABLE과 RESERVED 같은 확정 상태를 저장합니다. 좌석 조회 시 Redis 키가 존재하는 좌석만 응답에서 HOLD로 합성합니다.

결과 각 좌석은 실제로 선점된 시각부터 독립적으로 5분을 셉니다. 결제 성공·실패처럼 바로 반환해야 할 때는 TTL을 기다리지 않고 키를 삭제합니다.

화면의 5분 타이머만 믿으면 안 되는 이유

브라우저 타이머는 사용자 안내용입니다. 백그라운드 탭이나 네트워크 지연 때문에 Redis TTL과 끝나는 시점이 어긋날 수 있습니다.

결제 직전에 서버가 좌석 락을 다시 조회합니다. 키가 없으면 결제 시간이 지난 요청으로 거절하고, 저장된 회원 ID가 요청자와 다르면 다른 사용자의 좌석으로 판단해 거절합니다. 최종 결제 권한은 화면이 아니라 서버의 Redis 키와 소유자가 결정합니다.

예매 대기열에서 Redis를 사용한 방식

공연별 대기자는 Redis Sorted Set에 최초 진입 시각을 점수로 저장해 순서를 계산했습니다. 1초 주기 스케줄러는 예매 화면에 들어갈 사용자를 최대 50명까지 활성 Set으로 옮겼고, 결제 완료나 이탈 시 대기·활성 상태를 정리했습니다.

검증 범위

동일 좌석의 첫 요청만 성공하도록 구현했고 k6 예매 시나리오도 작성했지만, 저장소에 동시 요청 성공 건수·TPS·p95 결과가 남아 있지 않습니다. 확인되지 않은 성능 수치는 포트폴리오에 넣지 않았습니다.

05 · ENGINEERING PRINCIPLES

제가 중요하게 보는 것

  1. 성공의 기준을 하나로 정합니다.

    Redis 선점과 DB 발급 완료를 섞지 않습니다.

  2. 속도 수치에 측정 범위를 붙입니다.

    Ramp와 Burst, 쿼리와 API, 서버와 부하 발생기를 구분합니다.

  3. 장애 뒤의 상태를 설계합니다.

    실패 응답만 처리하지 않고 어떤 데이터를 기준으로 복구할지 정합니다.
